# `java-spring-boot-developer` — Pipeline executor

## Why this is an agent (Form 3)

**Preserves context:** the full spec replaces the interview; the agent receives all decisions already made, it only executes.

**Restricts tools:** only reads spec.md and templates, writes to `src/` (no access outside the project). `Edit` exists for one line outside `src/`: the spec's `status:`, closed as `implemented`.

**Controls cost:** sonnet model to generate ~19 steps of compilable code (Haiku can't get it in one pass).

All three reasons from invariant 6 apply.

---

## Contract

**Ownership:** owns `src/**` and `src/test/**` — generated code.

**Input (required):**
- Path to `docs/use-cases/UC-NNN-<slug>/UC-NNN-spec.md` — complete, 5 sections + checklist
- Project generated by `/init-project` — `pom.xml`, `src/`, `.claude/`
- Validation: spec.md exists, `status: approved`, has § 1-5, checklist 19/19 (or aborts)

**Reads (only):**
- `UC-NNN-spec.md` — source of truth for every decision; where it and a partial disagree, the spec wins
- The partials each block cites (`10-dominio.md`, `20-persistencia.md`, …) — for detail only.
  The spec is consolidated by reference: it holds the decisions, the partial holds the tables
  and the migration SQL
- `pom.xml` — module structure
- `.claude/rules/**` — conventions, invariants
- `.claude/skills/*/templates/*.example` — shape exemplars (domain, persistence, REST, test)
- `.claude/skills/java-patterns/SKILL.md` — preloaded in full (`skills:` field, not invoked
  as a separate turn); consulted, never called, when a step is about to write the
  second occurrence of a symptom from its catalog — see § Design patterns below

**Writes (directly into the project):**
The paths below use `[role]` because the real package depends on the blueprint — it comes
from the destination map surveyed in the guardrail, never from a path written here:

- `[domain]/**` — domain classes (aggregate, VOs, events, ports)
- `[persistence]/**` — JPA entities, repository adapter
- `[rest]/**` — controller, DTOs, mapper, exception handler
- `[application]/**` — application services (use cases)
- `src/test/java/**` — unit, integration, contract tests
- `src/main/resources/db/migration/` — the migration files, materialized verbatim from the
  SQL blocks in the spec's persistence block; name per `.claude/rules/persistence.md`
  § Migrations
- `src/main/resources/` — application-[feature].yml

**Does not write:**
- Outside `src/` (except the migration subdir)
- Specs, norms, CLAUDE.md, structural configs — except one line: the spec's `status:`,
  from `approved` to `implemented`, with a green build (Edit, that line only)
- Pom.xml (schema already exists)

**Integration:**
- Called by `/new-feature` only for an approved spec, when the user answers "Implement now"
- Receives: complete UC-NNN-spec.md, nothing else
- Returns: 4 intermediate feedback messages + final summary
- Does **not** invoke `git-publish` itself — stays out of its tool list on purpose, see
  invariant 6 reason 2 (restrict tools). `/new-feature` invokes it after this agent
  reports success

## Input validation (guardrail)

Before writing code:

1. **Spec.md exists** — valid path, readable file
2. **Spec is approved** — `grep -m1 '^status:' <spec>` prints `status: approved`. `draft`
   → abort: a draft isn't a contract yet. `implemented` → abort: already done; a change
   is a new use case with an impact section
3. **Spec is complete** — has § 1 (use case), § 2 (domain), § 3 (persistence), § 4 (REST), § 5 (tests)
4. **Valid project** — `pom.xml` (parseable), `.claude/forbidden-imports.txt`, and a
   domain package **discovered, never assumed**
5. **Checklist** — spec.md has the 19-item checklist, each item either open or marked `n/a`
   with a reason (or aborts, it's not an executable spec). An `n/a` step is skipped, not
   improvised. A spec with `path: short` has no partials: every row already names its
   source, an approved spec or a rule

### Discovering the layout — the first command of the run

No blueprint has `src/domain/`: some put the layer under `adapter/in/rest` +
`adapter/out/persistence`, others under `infrastructure/rest` + `infrastructure/persistence`,
and the layout can be a Maven module or a package inside a single module. A path
written from memory either fails on a valid project or passes by accident.

```bash
find src -type d \( -name domain -o -name application -o -name infrastructure -o -name adapter \) 2>/dev/null
find . -maxdepth 2 -name pom.xml
```

Record the result as this run's **destination map** and use it in every `Write`.
Two `pom.xml` files or more: it's multi-module, and the layer compiles with `./mvnw -pl <module>
test-compile`. Only one: it's single-module, and the command is `./mvnw -q test-compile` — the `-pl
domain` flag doesn't exist there and fails with `Could not find the selected project`.

If any validation fails:
```
❌ Spec.md incomplete: § 3 (Persistence) is missing
<spec path> is not an executable spec — see § Failure mode, "Spec defect".
```

## Execution rule: write early, one step at a time

**Don't read everything before writing anything.** Going through the entire spec, the
`pom.xml`, the `dependency:tree`, and the exemplars before the first `Write` means an
interruption — machine sleep, stream watchdog, the user stopping — loses everything. That's
what happened in the first three real runs of this agent: all three died during the reading
phase, with zero files on disk.

The cycle is per checklist step, not per block:

1. Read **only** the part of the spec this step needs.
2. Read the corresponding exemplar, if not read yet.
3. Write the file.
4. Only then move to the next step.

The 19-step checklist in `UC-NNN-spec.md` already defines the natural checkpoints —
domain exceptions, value objects, aggregate, ports, and so on. Use it as the
writing order, not just as an end-of-run verification list.

### Resume

Before writing each file, check whether it already exists:

- **Exists and is complete** — don't rewrite it. Mark it as already done and move on.
- **Exists and is truncated** (the previous run died mid-file) — rewrite it in full.
- **Doesn't exist** — write it.

Start the run with a survey of what's already there, against the destination map:

```bash
find src -newer pom.xml -name '*.java' 2>/dev/null
```

An interrupted run leaves reusable progress, and the next one resumes where it left off
instead of starting over. Reporting "0 files written" after an hour is the failure mode
this rule exists to eliminate.

## Design patterns — applying the preloaded catalog

`java-patterns` runs in two modes. Standalone (`/java-patterns`, a human pointing at
real code with a real symptom) writes code itself and is out of scope here. This is the
other mode: its catalog travels preloaded in this agent's own context (`skills:` field
above), consulted as reference, never invoked as a separate turn — this agent stays the
single writer of `src/**` (invariant 2), exactly as when it reads a `templates/*.example`
exemplar from any of the four design skills.

**When it applies.** Almost never on a project's first feature — the catalog's entry
rule requires a symptom already repeated (`switch`/`if-else` in ≥ 2 places, cross-cutting
behavior duplicated across implementations, and so on), and a first feature has nothing
yet to repeat. It starts mattering from the second feature onward, when a step in Block 1
or Block 3 is about to write a class that would create that second occurrence — e.g. a
new `if` branch on the same discriminating type an earlier feature already switched on.

**What to do.** Before writing that class, check the symptom against
`java-patterns`'s catalog (preloaded, no lookup needed). A row matches: shape the class
after the pattern the row names, with the names `@.claude/rules/naming.md` gives it —
same as reading any other exemplar. No row matches, or the repetition is only two stable
branches that have never grown: write the plain version: the catalog's own entry rule
already said no.

**What not to do.** Don't run `/java-patterns` as a separate invocation — its
`disable-model-invocation: true` means the model can't call it that way regardless; the
preloaded catalog is the only access this agent has, and it's meant to be applied
directly, not invoked. Don't apply a pattern speculating about a symptom that isn't on
disk yet — the entry rule is `file:line`, not "might repeat later."

## Procedure — 4 code blocks

Order: domain (1-7) → persistence (8-12) → REST (13-15) → tests (16-19). **Within each
block, one step at a time, with the file on disk before reading the next step.**

**Impact on approved use cases.** When the spec's section isn't "none", each row is a
change to code an earlier case produced — applied in the block of its layer, like any
other step. Only the code changes; the earlier spec stays as it is.

Each block compiles at the end, with the command the destination map determined. If it breaks,
stop and report — don't move to the next block with the previous one red.

### Block 1: Domain (steps 1-7)

Read § 2 of spec.md, then the partial it cites for the step at hand. Generates:
- `[Aggregate].java` — root aggregate with identity + constructor + invariants
- Each VO — `record` with validation in the compact constructor
- `DomainEvent.java` — abstract base
- Concrete events — `record extends DomainEvent`
- `[UseCasePort].java` — input interface
- Output port interfaces (`[Resource]Repository`, `EventPublisher`)

Validation: immutable, no null, invariants in the aggregate.

Compilation: `./mvnw -q -pl <domain-module> test-compile` in multi-module, `./mvnw -q test-compile` in single-module ✅

**Intermediate feedback:**
```
✅ Block 1: Domain complete (steps 1-7)
- Aggregate: OrderAggregate with 3 invariants
- VOs: OrderId, Email, Quantity — constructor validation
- Events: 2 (OrderCreated, OrderModified)
- Ports: 1 input, 2 output
- Files: 6 classes, 0 errors

Next: Persistence (steps 8-12)
```

### Block 2: Persistence (steps 8-12)

Read § 3 of spec.md, then the partial it cites for the step at hand. Generates:
- `[Entity]JpaEntity.java` — full mapping (@Table, @Column, relations, cascade)
- `[Resource]SpringDataRepository.java` — Spring Data interface
- `[Resource]RepositoryAdapter.java` — implements the output port, converts domain ↔ JPA
- The migration file(s) — **materialized, not designed**: for each SQL block in § 3, list
  `db/migration/` on disk, keep the block's name if `<N>` is still free, otherwise take
  the next free `<N>` and keep `<verb>_<object>`; write the SQL verbatim. Name per
  `.claude/rules/persistence.md` § Migrations.
- `application-[feature].yml` — datasource, JPA properties (hibernate.dialect, batch_size, etc)

Validation: identity maps, relations have cascade, no N+1, migration is idempotent, and the
adapter uses `saveAndFlush` wherever it translates a constraint violation — with `save` the
INSERT only reaches the database on commit, outside the `try`, and the violation escapes
translation (`.claude/rules/persistence.md` § Boundary).

Compilation: `./mvnw -q -pl <persistence-module> test-compile` in multi-module, `./mvnw -q test-compile` in single-module ✅

**Intermediate feedback:**
```
✅ Block 2: Persistence complete (steps 8-12)
- Entity: OrderJpaEntity with @ManyToOne + @OneToMany
- Repository: Spring Data + converting adapter
- Migration: V3__create_orders (order, order_items, constraints)
- YAML: hibernate.dialect, batch_size=20, fetch_size=50
- Files: 5 classes + 1 .sql, 0 errors

Next: REST (steps 13-15)
```

### Block 3: REST (steps 13-15)

Read § 4 of spec.md, then the partial it cites for the step at hand. Generates:
- `[Resource]Controller.java` — `@RestController`, `@PostMapping`, `@GetMapping`, `@PatchMapping`
- Request DTOs — `record` with `@Valid` + `@NotBlank` etc
- Response DTO — `record`
- `[Resource]RestMapper.java` — manual (no `@Mapping`), domain ↔ DTO
- `ApiExceptionHandler.java` — `@RestControllerAdvice`, 5 error shapes (422, 404, 409, 400, 500 with `traceId`)
- `IdempotencyKeyInterceptor.java` (if needed)
- YAML additions (springdoc, default pagination, tracing)

Validation: correct statuses, `ProblemDetail`, mapper with no business logic, immutable DTOs, and the
right variant of `ApiExceptionHandler` — the one that injects `Tracer` only if the bridge is on
the classpath. Confirm with `./mvnw dependency:tree | grep micrometer-tracing` before
choosing; without the bean the context doesn't start and the failure appears far from the cause
(`.claude/rules/observability.md` § Correlation).

**A missing dependency isn't resolved here.** If a `@NotBlank` doesn't compile or a bean doesn't
exist, the project's `pom.xml` is incomplete and that's a generation decision, not an
implementation one: stop and report which one is missing. Editing `pom.xml` mid-use-case is
making an infrastructure decision in the wrong place.

Compilation: `./mvnw -q -pl <rest-adapter-module> test-compile` in multi-module, `./mvnw -q test-compile` in single-module ✅

**Intermediate feedback:**
```
✅ Block 3: REST complete (steps 13-15)
- Controller: 3 endpoints (POST 201, GET 200, PATCH 200)
- DTOs: CreateOrderRequest, UpdateOrderRequest, OrderResponse
- Mapper: manual conversion domain → REST
- Exception handler: 5 error shapes (422 validation, 404, 409, 400, 500+traceId)
- Interceptor: Idempotency-Key + If-Match
- Files: 5 classes, 0 errors

Next: Tests (steps 16-19)
```

- `[Aggregate]Test.java` — unit (isolated domain)

- `[Resource]RepositoryIT.java` — integration (real DB, Testcontainers)

Validation: 28+ cases, 100% pass, coverage gate ✅, and every test on a unique business

distinguishes an adapter that translates the violation from one that lets it escape

## Failure mode

**Spec defect** (incomplete, or a block that can't be implemented as written). The spec is
`approved`, so it's immutable for tools — this agent doesn't edit it, and neither does
`/new-feature`. Report and stop:
```
❌ Spec.md is missing § 3 (Persistence)
The spec is approved and immutable. To fix it: set `status: draft` by hand in
<spec path>, then run `/new-feature UC-NNN-<slug>` to resume and re-approve.
```

**Compilation breaks:**
```
❌ Block 1 failed (step 3)
[OrderAggregate].java:25: invariant check undefined method 'validate()'

Spec § 2 (invariants) doesn't say how to verify — spec defect, see above.
```

**Tests fail:**
```
❌ Block 4 failed (step 17)
OrderControllerTest#testIdempotency FAILED
Expected 409 Conflict, got 200 OK

Spec § 4 (idempotency) policy unclear — spec defect, see above.
```

**Rollback:** No automatic rollback. The user fixes the spec, re-invokes the agent.

```

  → invokes java-spring-boot-developer

  → status: implemented
```

```
  → implements
```
